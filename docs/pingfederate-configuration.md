# PingFederate configuration expected by the test

The test exercises exactly one measured path: a confidential client
authenticates with client credentials and performs an RFC 8693 token
exchange using a self-signed subject token. **User authentication is not
part of the test** — subject tokens are generated by the load generator,
signed with a predefined RSA key, and validated by PingFederate against the
matching public JWKS. No user store, no password grant.

## Objects required

1. **JWT access token manager** for the requested (output) token — RS256,
   centralized signing key.
2. **JWT token processor** validating the subject tokens: allowed issuer
   `https://pf-perf-subject`, allowed audience `perf-test-client`,
   verification key = the embedded JWKS from the server profile
   (`perf-subject-jwks.json`, produced by `make keys`).
3. **Token Exchange Processor Policy (TEPP)** mapping subject token type
   `urn:ietf:params:oauth:token-type:access_token` to that processor, with
   the contract attribute `subject` fulfilled from `SUBJECT_TOKEN.sub`.
4. The TEPP set as the **default token exchange processor policy** (and also
   assigned directly to the client via `tokenExchangeProcessorPolicyRef`).
5. **`perf-test-client`** — confidential client with the token-exchange
   grant enabled and `client_secret_basic` authentication. Its credentials
   are presented on every measured request.

Successful responses must contain both `access_token` and `issued_token_type`.

## How this project provides the configuration

`server-profiles/pingfederate-token-exchange/` is a Ping Identity server
profile in Ping's documented bulk-config format:

- `instance/bulk-config/data.json.subst` — declarative configuration for all
  six objects above. The PingFederate image expands its `${VARIABLES}` from
  container environment variables at startup and imports the result through
  `/pf-admin-api/v1/bulk/import`, then replicates the configuration to the
  engine Pods. No custom scripts run.
- `instance/server/default/data/perf-subject-jwks.json` — the public
  verification JWKS matching `keys/subject-signing.key`.

Push that directory to a git repository you own and point `SERVER_PROFILE_URL`
at it (see `.env`). If the repository is private, create the chart's git
secrets so the Pods can clone it:

```bash
kubectl -n pf-perf create secret generic pf-pingfederate-admin-git-secret \
  --from-literal=SERVER_PROFILE_GIT_USER=<user> \
  --from-literal=SERVER_PROFILE_GIT_PASSWORD=<pat>
kubectl -n pf-perf create secret generic pf-pingfederate-engine-git-secret \
  --from-literal=SERVER_PROFILE_GIT_USER=<user> \
  --from-literal=SERVER_PROFILE_GIT_PASSWORD=<pat>
```

`make deploy` passes the substitution variables (`SUBJECT_ISSUER`,
`SUBJECT_AUDIENCE`, `PERF_CLIENT_ID`, `PERF_CLIENT_SECRET`, the JSON-escaped
JWKS as `PERF_SUBJECT_JWKS`, and `OUTPUT_ISSUER`/`OUTPUT_AUDIENCE`) into the
admin container. `PERF_CLIENT_SECRET` must equal `CLIENT_SECRET` in `.env` —
the import creates the client with that secret, and the k6 Pods authenticate
with it on every request.

The bulk import is destructive by design: the profile represents the full
desired state of this lab instance, and every admin restart re-imposes it.
Do not hand-edit configuration in the admin console — changes are lost on
the next redeploy.

## Manual verification after deploy

```bash
! kubectl -n pf-perf logs deploy/pf-pingfederate-admin -c pingfederate-admin | grep -i bulk
```

`INFO: Removing Imported Bulk File` confirms the import succeeded. On
failure the log prints the API's error response for each failed item
(`failFast=false`), which names the object and field to fix.

The benchmark is meaningful only when the runtime configuration is identical
on both engine Pods — which cluster replication guarantees; never edit one
engine's configuration independently.

## Rotating the subject signing key

The subject key must remain stable: every token k6 signs must verify against
the JWKS in the profile. Regenerate only deliberately
(`./scripts/generate-signing-key.sh --force`), re-push the profile, and
redeploy before the next test.
